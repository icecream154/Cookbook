# 01. 正交八层架构、模块职责红线与二级分包法则

本文档规定产品规格实例库（`spec/`）的**标准顶层目录结构、各层准入与越界禁令红线，以及当规模扩大时的二级子目录正交划分法则与具体文件概念释义**。

> **阅读说明**：本文档属于跨项目通用的元规范，文中所有“通用示例”均以常见的在线交易/预订系统（如商品、订单、结算）作为中性教学示意，不绑定任何特定业务项目。

---

## 1. 标准顶层目录拓扑

任意遵循本元规范的产品规格库（`spec/`），其顶层结构固定由 1 份导航总入口与 `01` ~ `08` 八个职责正交的业务规格层构成：

```text
spec/
├── README.md                        # 产品规格总导读（产品背景、命名空间速查表、全量文档索引、角色阅读路径）
├── 01-vision-and-scope.md           # 第 1 层：产品愿景、目标人群场景、功能版图与非目标边界、全局非功能约束
├── 02-domain-model/                 # 第 2 层：静态领域模型（业务术语定义、实体字段契约、全局标准枚举字典）
├── 03-business-rules/               # 第 3 层：全局动态业务规则库（跨领域计算、判定矩阵、过滤与降级兜底策略）
├── 04-ia-and-flows/                 # 第 4 层：信息架构与端到端流程（多端导航容器壳、跨页面业务流与状态同步）
├── 05-components-and-patterns/      # 第 5 层：公共业务组件与交互契约（跨页复用 UI 组件、全局通用交互状态机）
├── 06-pages/                        # 第 6 层：单页与子视图规格书（区块排版、字段绑定、页面状态枚举、交互事件表）
├── 07-metrics-and-tracking/         # 第 7 层：数据度量与埋点字典（北极星与转化漏斗公式、关键业务事件及属性契约）
└── 08-verification/                 # 第 8 层：验收与可交互原型（三段式验收用例表、单页全状态线框原型、跨页联动微原型）
```

## 2. 八层职责准入边界与越界禁令红线（含正反判定示例）

为防止同一业务事实在多处重复抄写并随演进产生分歧，各层必须严格遵守以下**准入范围**与**越界禁令**：

| 层级 | 允许承载的信息（职责准入 + ✅ 正确示例） | 严禁写入的信息（越界禁令 + ❌ 错误反例） |
| :--- | :--- | :--- |
| **`01` 愿景与范围** | 痛点背景、一句话定位、目标人群场景、当前纳入的功能版图、明确排除的非目标边界（Non-Goals）、全局非功能约束。<br>✅ *示例：定义“纳入多币种跨境结算能力；暂不自建跨境物流仓储”。* | 严禁展开具体数据库字段、算法公式或页面按钮位置。<br>❌ *反例：在 `01` 中写“订单表需包含 `currency_code` 字段，保留两位小数四舍五入”。* |
| **`02` 领域模型** | 业务专有术语标准定义、静态数据实体的字段名/类型/必填约束、全局标准枚举编码与展示文案。<br>✅ *示例：定义 `Order` 实体的结构字段，以及 `OrderStatus` 枚举含待付款/待发货/已取消。* | 严禁混入动态推荐/计价/超时流转等运行期规则，严禁规定 UI 控件形态。<br>❌ *反例：在字段说明里写“未支付超过 15 分钟自动关单，并在页面右上角标红字”（前者属 `03`，后者属 `06`）。* |
| **`03` 业务规则** | 横跨多个实体或页面的计算公式、布尔过滤条件、多分支决策矩阵、数据冲突裁决、空结果或异常时的业务降级兜底。<br>✅ *示例：定义“满减券与会员折扣叠加优先级矩阵，以及库存不足时的拆单兜底规则”。* | 严禁描述页面栅格排版、抽屉滑出方向或按钮摆位等界面布局细节。<br>❌ *反例：在规则文档中写“优惠金额用 16px 橙色加粗字体展示在提交按钮左侧”。* |
| **`04` 架构与流程** | 全站页面父子层级地图、手机/平板/电脑不同屏幕宽度下的公共外框导航壳、用户跨多个页面完成任务的跳转路径与数据同步时机。<br>✅ *示例：绘制“购物车 → 确认订单 → 支付收银台 → 支付结果页”的流转及支付后返回自动清空购物车的同步关系。* | 严禁在跨页流程图中塞入单页内部的细碎输入框格式校验，严禁抄写组件字段。<br>❌ *反例：在跨页流程图里画 5 个菱形分别校验“手机号是否 11 位、邮编是否纯数字”。* |
| **`05` 组件与交互** | 在 **`>= 2` 个独立页面/空间**中复用的复合业务 UI 组件及其场景变体、跨页面共用的通用交互处理机制。<br>✅ *示例：定义在首页、搜索页、收藏页共用的“商品摘要卡片”，以及“未登录点击受限操作时弹出登录框、登录成功后自动替用户完成原操作”的通用机制。* | 严禁收录仅在某一个页面单独出现的一次性局部区块。<br>❌ *反例：把只在“个人设置页”出现一次的“关于我们版本号展示块”放进公共组件层。* |
| **`06` 页面规格** | 单个页面或高复杂度抽屉/弹窗的出入口与权限、多端区块排布、组件组装与字段绑定、该页面完整状态枚举、用户动作触发规则与埋点的映射表。<br>✅ *示例：声明“结果列表区挂载 `05` 层的商品摘要卡片（搜索变体），点击加购时调用 `03` 层的库存校验规则并触发 `07` 层的加购埋点事件”。* | **三不抄铁律**：严禁平铺抄写枚举值全集（须链接 `02`）、严禁重写计算公式（须链接 `03`）、严禁重复描述公共组件与通用交互细节（须链接 `05`）。<br>⚠️ *注意：“不抄定义”绝不等于“只甩裸编号”，引用时须附带中文名与括号微摘要（如写 `[ENUM-ORD-PayType 支付方式]（微信/支付宝等 4 类）`），兼顾唯一事实源与免跳转流畅阅读。*<br>❌ *反例：在“订单列表页”和“订单详情页”两份文档里把 6 种订单状态编码表各自手抄一遍，后续改名时漏改导致前后矛盾。* |
| **`07` 指标与埋点** | 北极星指标定义、核心业务漏斗转化率公式、支撑指标计算的关键业务事件触发时机与必传业务属性。<br>✅ *示例：定义“结算转化率计算公式”及底层 `checkout_submitted` 事件的必传业务属性契约。* | 严禁堆砌无任何指标消费的无效曝光埋点，严禁绑定特定第三方埋点 SDK 代码。<br>❌ *反例：在规格中直接写入 `window.sensors.track(...)` 具体前端埋点调用代码。* |
| **`08` 验收与原型** | 承载三类把文字规格落到实处的验证资产：<br>1. **结构化验收测试用例表**：按“前置条件 → 触发操作 → 预期结果”（`Given-When-Then`）逐条编写的测试核对清单；<br>2. **单页全状态线框原型（HTML）**：只用灰阶线框画布局结构，在网页顶部提供一排状态切换按钮，无需前置操作即可一键切出单个页面的正常态、空数据态、报错态等全部界面切面；<br>3. **跨页关键动线微原型（HTML）**：仅串联 2~3 个强关联页面，在浏览器中真实演示“跨页面传值、登录拦截恢复”等连续动态交互。<br>✅ *示例：① 验收表写明“前置：已勾满 100 减 20 券且合计 105 元 → 操作：取消勾选 10 元商品 → 预期：自动退券、实付变 95 元并提示差额”；② 打开购物车原型 `cart.html`，点顶栏 `[正常有货]` / `[空购物车]` / `[含失效商品]` 按钮直接预览三种界面；③ 打开 `guest-buy-flow.html` 亲手走通“游客点购买 → 弹登录框 → 登录后自动带规格进结算页”。* | 严禁把整个应用所有模块写成大而全的单体前端工程；严禁在原型中私自添加 `01`~`06` 未定义的野生功能；严禁提前介入高保真品牌配色与视觉精修。<br>❌ *反例：写一个几千行代码的巨型单页商城 Demo，评审者想看一眼“结算页含失效商品提示”还得先手动从登录、搜商品、加购物车一路点十步才能凑出条件；或在产品原型里耗费精力调圆角渐变阴影，越界替代下游 UI 设计工作。* |

## 3. 二级子目录与渐进式分包法则（像组织代码 Package 一样弹性下钻）

当某一层的规格内容增多时，严禁把所有信息堆砌在少数大文件里造成认知过载，也严禁随意按个人习惯切分。本规范确立两条核心组织原则：

1. **正交分类轴恒定**：每一层必须沿着本层专属的语义维度切分（见下表）。
2. **目录深度随规模像代码包（Package）一样弹性下钻**：小规模模块采用扁平文件避免过度设计的空壳目录；一旦单个文件承载的内容超出认知负荷（**建议拆分水位线：单文件超过 `5` 个核心实体/规则/组件，或正文超过 `250~300` 行**），必须沿同一分类轴继续向内划分子目录（子包）乃至“一对象一文件”，并在各级目录放置 `_index.md` 充当包导出入口（如同代码中的 `index.ts` / `__init__.py`）。

| 层级 | 核心拆分原则（按什么逻辑切分，为什么这么拆） | 目录与文件组织方式（轻量形态 vs 大规模下钻形态） |
| :--- | :--- | :--- |
| **`01` 愿景与范围** | 聚焦产品整体定位与能力边界，作全局宏观统领，一般不拆分。 | 默认单文件 `01-vision-and-scope.md`（若为包含多个独立子产品的超大型产品矩阵，可按子产品线拆分子文件）。 |
| **`02` 领域模型** | **先按业务数据的归属边界（一级业务域，如会员域、商品域、订单域）建文件夹；复杂大域内部继续像代码包一样按二级业务模块拆分**。 | 每个域内信息按性质分为三类：**业务术语**（`terms.md`）、**数据表实体**（`entities.md`）、**标准枚举值**（`enums.md`）。小型域直接平铺这 3 份文件；大型复杂域在域内继续建子模块目录，乃至拆成“一张核心表一个文件”（详见 [3.1 节](#sec-3-1)）。 |
| **`03` 业务规则** | **不按静态数据表拆，而按“系统执行的业务决策主题”（如计价优惠、库存分配、退款准入）拆文件**，解决一条规则同时读取多张数据表的归属冲突。 | 常规规模直接在目录下按决策主题建文件（如 `pricing.md`、`inventory.md`）；若单个决策主题规则极多，可升级为同名子文件夹再按细分场景拆多份文件（详见 [3.2 节](#sec-3-2)）。 |
| **`04` 架构与流程** | **把“全站共用的外框导航骨架”与“用户跨页面办事的具体路线图”分开；跨页流程再按用户使用产品的先后阶段分文件**。 | 根部单放 `ia-and-shell.md`（定义全站页面结构图与手机/平板/电脑导航栏变形规则）；所有跨页流程图放入 `flows/` 子目录，按注册引导、搜索选购、下单支付等旅程阶段分文件存放（详见 [3.3 节](#sec-3-3)）。 |
| **`05` 组件与交互** | **将在 `>= 2` 个页面复用的设计资产分为两类：“看得见的复用 UI 零件”与“跨页面通用的交互处理机制”**。 | 组件较少时放两份文件：`shared-components.md`（如商品卡片、数量加减器）+ `interaction-patterns.md`（如未登录拦截后自动恢复原操作、删除后 4 秒撤销提示）；规模变大后升级为 `components/` 与 `patterns/` 两个子目录，按单个组件/机制拆独立文件（详见 [3.4 节](#sec-3-4)）。 |
| **`06` 页面规格** | **先按一级导航业务板块（功能空间）建文件夹；同一板块内，把“主页面”与“复杂的专属抽屉/弹窗/全屏子页面”拆成平级独立文件**，防止把弹窗细节全塞进主页面导致单篇几千行。 | 每个业务板块建一个子目录（如 `search/` 搜索板块、`checkout/` 结算板块），目录内将主页面（如 `search-main.md`）与高复杂度附属子视图（如 `filter-drawer.md` 高级筛选抽屉）拆开并列存放；超大型后台工作台板块可在内部继续按子模块建二级目录（详见 [3.5 节](#sec-3-5)）。 |
| **`07` 指标与埋点** | **把“业务看什么指标、怎么算转化率”与“研发在代码里何时上报什么埋点事件”拆开分文件管理**，通过编号互相绑定，杜绝乱提没人看的埋点。 | 中小规模放两份文件：`metrics-funnel.md`（写北极星指标与各漏斗转化率计算公式）+ `event-dictionary.md`（写支撑公式所需的每个埋点事件名、触发时机与必传字段）；当埋点事件上百个时，升级为 `metrics/` 与 `events/` 两个子目录并按业务模块拆多份文件（详见 [3.6 节](#sec-3-6)）。 |
| **`08` 验收与原型** | **先将“文字版验收测试用例表”与“浏览器可点击的线框 HTML 原型”分开；HTML 原型拒绝做成单个巨型网页，进一步拆成“看单个页面全部状态的页面”与“看跨页面连续交互的页面”**。 | ① **文字验收表**：默认放 `acceptance-criteria.md`（用例极多时建 `acceptance/` 子目录按业务模块拆分）；<br>② **可交互原型目录 `prototypes/`** 下固定分 4 块：`index.html`（原型总导航入口页）、`shared/`（所有原型共用的灰阶线框样式与标准模拟假数据）、`pages/`（与 `06` 各板块对应的单页面原型，网页顶部可一键切换正常态/空数据态/报错态）、`flows/`（串联 2~3 个页面演示登录拦截恢复、跨页传值的小型演示页）（详见 [3.7 节](#sec-3-7)）。 |

### <a id="sec-3-1"></a>3.1 `02-domain-model/`：如何像代码领域层一样支持多级分包与防过载拆分？

领域模型是全库的数据地基。如果规定一个业务域无论多大都只能塞进三个单文件，一旦遇到复杂的核心域（例如包含正向交易、支付结算、履约拆单、逆向退款几十张表的“订单大域”），单文件就会膨胀到数千行而彻底失控。因此，领域模型采用“**三类信息契约恒定 + 三级目录深度按需弹性展开**”的包结构：

1. **三类基础信息契约（无论目录拆几层，内容性质严格三分）**
   - **业务术语（`terms`）**：消除团队口语歧义的专有概念词典。*示例：严格定义“**可售库存** = 物理在库总数 − 已下单未支付锁定量 − 残次冻结量”，防止研发与运营各执一词。*
   - **静态实体（`entities`）**：需要持久化落库或跨端传输的业务对象字段结构表（对应数据库表或领域 Model）。*示例：定义订单实体 `Order` 包含订单号、买家 ID、实付金额（分）、状态等字段及必填约束。*
   - **标准枚举（`enums`）**：字段或筛选项中所有取值封闭、全站统一文案的选项字典。*示例：定义 `OrderStatus` 封闭列举 `UNPAID（待付款）`、`PAID（待发货）`、`COMPLETED（已完成）`，杜绝不同页面叫法不一。*

2. **三级弹性包结构示范（同一个项目内允许不同复杂度的域并存）**
   - **形态一（轻量平铺包）**：子域仅有 `2~5` 个实体时，直接在 `<domain>/` 下平铺 `terms.md`、`entities.md`、`enums.md`。
   - **形态二（按聚合簇 / 二级业务模块嵌套子包）**：当某个核心域包含多个相对独立的业务子块时，像组织代码 Package 一样在域内继续建立子目录，并在域根目录放置 `_index.md` 汇总本域内部关系。
   - **形态三（按单聚合根 / 单枚举组拆独立文件）**：当某一个核心聚合本身就包含十余张主子表或极多字段时，进一步将 `entities.md` 升级为 `entities/<aggregate>.md` 目录，实现“一聚合一文件”。

```text
02-domain-model/
├── _index.md                        # 全局跨域上下文映射图 (Context Map) 与一级域导航
├── member/                          # 【形态一：轻量域】仅 3 个实体，直接平铺，干净无冗余层级
│   ├── terms.md
│   ├── entities.md
│   └── enums.md
└── order/                           # 【形态二/三：大型复杂域】像代码包一样按聚合簇递归下钻，防止信息堆砌过载
    ├── _index.md                    # 本域包导出入口（类似 index.ts）：绘制域内 ER 图并索引各子包
    ├── terms.md                     # 本域通用的基础交易术语
    ├── trade-core/                  # 子包 1：正向交易与支付聚合簇
    │   ├── entities/                # [形态三] 单聚合字段极多时，拆为独立文件
    │   │   ├── order.md
    │   │   └── payment-slip.md
    │   └── enums.md
    ├── fulfillment/                 # 子包 2：履约拆单与物流包裹聚合簇
    │   ├── entities.md
    │   └── enums.md
    └── after-sales/                 # 子包 3：逆向退款与售后争议聚合簇
        ├── terms.md
        ├── entities.md
        └── enums.md
```

### <a id="sec-3-2"></a>3.2 `03-business-rules/`：为什么按“业务决策能力簇”拆文件，而不按静态实体拆？

- **核心原因**：真实的业务规则几乎都是**跨多个静态数据域联合读取**的。*例如“订单结算凑单计价规则”，既要读 `member/` 域的会员等级折扣，又要读 `catalog/` 域的商品类目满减门槛，还要读 `order/` 域的应付总额*——如果强行把规则塞进某一个静态实体目录，就会导致严重的归属冲突。
- **正确拆法**：按系统需要做出的**核心业务决策能力**建立专题文件（若单一能力簇规则极多，可升级为同名子目录继续拆分）。
  - *通用示例*：在电商系统中，可将 `03-business-rules/` 拆分为 `pricing-and-promotion.md`（计价与优惠叠加规则簇）、`inventory-allocation.md`（库存锁定与拆单规则簇）、`refund-eligibility.md`（售后退换货准入判定规则簇）。

### <a id="sec-3-3"></a>3.3 `04-ia-and-flows/`：什么是“全局拓扑与多端导航壳”以及“按用户旅程拆流程”？

如果把整个软件比作一座商场，在设计每一间具体商铺（`06-pages/`）之前，必须先把“**商场的楼层地图与公共走廊扶梯标准**”和“**顾客从进门逛街到收银台结账的行走路线**”定下来。因此本目录固定拆分为 **1 份公共外框文档**与 **1 个跨页路线文件夹**（具体表格列写法见后续 [03-authoring-templates.md 第 2.4 节](./03-authoring-templates.md#tpl-flow)）：

```text
04-ia-and-flows/
├── ia-and-shell.md                      # 静态公共外框：全站页面地图 + 手机/平板/电脑外壳与弹窗变形规则
└── flows/                               # 动态跨页路线：用户跨越多个页面办事的连贯动线与数据同步
    ├── _index.md                        # 流程总目录 + 全局跨页面数据同步总表
    ├── 01-onboarding-and-auth.md        # 旅程阶段 1：新手引导与注册登录流
    ├── 02-browsing-and-search.md        # 旅程阶段 2：商品搜索、筛选与加购流
    └── 03-checkout-and-fulfillment.md   # 旅程阶段 3：合并结算、支付与履约流
```

#### 1. `ia-and-shell.md`（全站页面地图与多端公共外框）：一次性定好四块公共地基
把公共导航栏、屏幕网格和弹窗变形规则在这里统一规定好之后，后面写几十份具体单页文档时就不用每页重复抄写导航栏了。它包含四个核心部分：

- **① 全局导航拓扑与切页记忆规则**（全站页面地图 & 路由规则）
  - **全局导航拓扑**（即“全站页面关系地图”）：一张俯瞰整个应用的地图，标明全站一共有哪几个一级主板块、二级内页、复杂大抽屉和全局弹窗，以及谁从谁点击进入。**画多细的边界**：地图只画到“值得在 `06-pages/` 单独写一篇文档的独立页面或复杂大抽屉”为止；页面内部的局部小标题、普通按钮或一句“确定删除吗？”的简单确认框绝不画进去，防止地图乱成蜘蛛网。
  - **一级导航席位与游客可达性**：规定主导航栏摆哪几个入口、打开应用默认落到哪一页、未登录游客点进去怎么展示。*短例：规定底部依次放“首页 / 搜索 / 购物车 / 我的”，游客点“购物车”允许直接进入看到引导说明页，严禁在点击主导航图标时粗暴弹出登录框把人拦在门外。*
  - **跨栏切换状态保活**（Keep-Alive，即“切走再切回的记忆能力”）：规定用户在 A 板块滑到列表第 30 条并勾好了筛选条件，切去 B 板块看一眼再切回 A 板块时，是否原样保留刚才的滚动位置与筛选项，避免每次切换都被迫滚回顶部重新加载。
  - **深链无历史栈兜底回退**（即“点外部分享链接直达内页时，点返回退去哪”）：“深链（Deep-Link）”指用户点开微信分享链接或直接刷新浏览器，空降进入某个二级内页；此时浏览器里没有站内“上一页”浏览记录（即“无历史栈”）。必须规定此时点击左上角 `[← 返回]` 默认退回哪个主页（*短例：从分享链接直达“商品详情页”后点返回，因无上一页记录，默认兜底退回“商城首页”而不是点不动卡死*）。

- **② 多端视口断点与画布栅格基线**（不同屏幕宽度下的尺子与对齐网格）
  - **视口与断点**（Viewport & Breakpoint）：“视口”就是屏幕当前的可见窗口宽度；“断点”是触发布局变形的分界线像素值。*短例：窗口宽度 `< 768px` 按手机竖屏排版，`768 ~ 1023px` 按平板排版，`>= 1024px` 按电脑宽屏排版。*
  - **设计基准宽、版心上限与安全边距**：“设计基准宽”是设计师画图的标准画布宽度（*如手机按 `390px` 宽出图*）；“版心上限”是电脑大屏下中间内容区的最大宽度（*如限制主内容最宽 `1200px` 居中两侧留白，防止在超宽显示器上文字拉成极长一行无法阅读*）；“安全边距”是内容离屏幕边缘的留白，以及避开手机顶部刘海摄像头、底部全面屏上滑小黑条的预留高度。
  - **画布栅格列数与槽宽**（Grid & Gutter）：像带暗格的信纸一样，把页面宽度等分成若干竖列（栅格列数）与列间留白（槽宽），用来把大小卡片对齐。*短例：手机分 `4` 列（列间距 `12px`），平板分 `8` 列，电脑分 `12` 列（列间距 `24px`）。*
  - **一级导航栏跨端变形尺寸**：公共主导航在不同屏幕上的长相与像素宽高。*短例：手机端是贴在屏幕底部的固定横栏（高 `60px`，方便单手大拇指点按）；平板端变形为贴在屏幕最左侧的窄图标竖条（叫“导航轨 Navigation Rail”，宽 `76px`，不占宝贵的上下高度）；电脑端展开为左侧带图标和完整文字的菜单侧栏（宽 `220px`）。*

- **③ 容器壳插槽、标准分栏骨架与外框层级退化**（公共相框分区、通用户型图 & 进内页时的导航显隐）
  - **容器壳与插槽**（App Shell & Slots）：“容器壳”就像相框，是包裹在具体业务画面外围的公共导航与顶底外框；“插槽”是相框预留好的固定摆放槽位（*如主导航槽、顶部标题返回槽、中间主内容滚动槽、底部吸底操作按钮槽*）。
  - **标准分栏骨架**（主内容区的“通用户型图”）：把中间主内容区常见的跨端排布规律提炼成全站共用的几套排版骨架，**严禁**把某一个具体单页（如某详情页）的私有业务字段塞进全局外框表里。*短例：提炼出“卡片网格骨架（手机排 1 列 → 平板排 2 列 → 电脑排 3 列）”和“主副双栏骨架（手机上下单列流 → 电脑左宽栏滚图文详情 + 右窄栏吸顶固定结算卡）”，后续 `06-pages/` 的每个单页只需声明“本页套用哪套骨架”即可。*
  - **外框层级退化**（即“越往内页走，公共导航栏如何按需隐藏让路”）：当用户从浅入深进入不同深度的页面时，外层导航栏的显隐规则：
    - **一级根页**（点主导航直接打开的首页、搜索页等）：完整显示主导航栏；
    - **二级推入页**（从列表点进去的商品详情页、收货地址编辑页）：*手机屏幕小，自动隐藏底部四栏主导航，换成顶部的 `[← 返回]` 和底部的 `[立即购买]` 专属操作栏；而平板和电脑屏幕足够宽，左侧主导航栏保持常驻显示，方便随时切去别的板块*；
    - **全屏专注页**（需要用户全神贯注、严防误触打断的沉浸页面，如全屏视频跟练、在线考试答题页）：手机、平板、电脑三端统一隐藏全部全局主导航栏，只留右上角 `[退出 ✕]`。

- **④ 次级容器跨端变形与 Z 轴叠放梯队**（弹窗/抽屉随屏幕变形 & 多层浮窗谁盖在谁上面）
  - **次级容器**（浮在当前页面上方的四类附属弹层）：不新开整张页面，而是临时叠在宿主页面之上的面板——① **抽屉**（从屏幕底边往上滑出的半屏面板，或从侧边滑出的侧栏，如筛选面板）；② **模态框**（屏幕正中央弹出的卡片窗口，背后带半透明黑底“遮罩”锁住底层页面不让乱滚，如登录框）；③ **悬浮小窗**（挂在角落不挡正文阅读的迷你窗，如小窗播放视频）；④ **轻提示**（浮现几秒自动消失的短提示条 Toast，或底部带 `[撤销]` 按钮的黑条提示 Snackbar）。
  - **跨端变形规则**：同一个附属面板在不同设备上自动变成最顺手的形态。*短例：“多维筛选面板”在手机上从底部滑出半屏抽屉，在平板上从右侧滑出侧边栏，到了电脑宽屏则直接摊开嵌在页面左侧常驻显示（不用点按钮开关，勾选筛选项右侧商品列表实时刷新）。*
  - **Z 轴叠放梯队**（Z-Index，即“垂直屏幕方向谁盖住谁的高低顺序”）：把屏幕想象成一摞叠放的透明玻璃纸，必须明确多层浮窗同时出现时的上下顺序，防止遮挡事故。*短例：用户在手机上先打开了“筛选抽屉”（设为第 5 层），在抽屉里点某开关触发了“登录弹窗”（必须设为更高的第 6 层）——若没规定高低，登录框就会弹在筛选抽屉背后被严严实实挡住；又如手机底部的“已删除 · [撤销]”提示条必须设在最高层，并向上抬高避开底部 `60px` 的主导航栏，否则会被导航栏盖住点不到。*

#### 2. `flows/<stage>.md`（按用户旅程拆分的跨页办事路线）：把动态连贯操作讲清楚
单页文档只管“停在某一个房间里长什么样”，而 `flows/` 专门负责把“**用户为了办成一件事，连续跨越 2 个以上页面的完整路线**”串联起来：

- **按用户价值旅程阶段分文件**：按用户从初次接触到深度使用产品的自然先后顺序拆成多份文件（*如先有 `01-onboarding-and-auth.md` 注册建档阶段，再有 `02-browsing-and-search.md` 找货选品阶段，最后是 `03-checkout-and-fulfillment.md` 下单支付阶段*）。
- **每条跨页流程必讲清的四件事**：
  1. **前置条件**：出发前用户处在什么状态（*如“未登录游客，在商品详情页已选好尺码与数量”*）；
  2. **标清归属的跨页流程图**：图里每个页面方框对应哪个具体页面、每个判断分叉对应哪条业务规则都逐一标明，杜绝画出一个后续根本找不到规格书的“幽灵页面”；
  3. **中断与异常回退**：用户走到一半关掉弹窗、点返回或遇到断网报错时，如何干干净净退回原状而不留残余脏数据（*如“游客点购买弹出登录框后主动点关闭，立即清空挂起的购买意图，原商品页保持不变”*）；
  4. **跨页状态与缓存同步**（并在 `flows/_index.md` 汇总成全局同步总表）：正因为前面开启了页面缓存“保活”，当用户在 B 页面改了数据后，必须明确写清切回早已打开的 A 页面时怎么同步刷新，防止用户看到过期的旧画面。*短例：用户在“确认订单页”付款买走了购物车里的 2 件商品，当他点返回回到之前打开过的“购物车页”时，那 2 件已买商品必须自动从缓存列表中移除并重算合计金额，绝不能还留在列表里让用户误以为没买成功。*

### <a id="sec-3-4"></a>3.4 `05-components-and-patterns/`：“有形复合组件”与“无形跨页交互契约”有什么区别？

凡在 **`>= 2` 个页面**重复出现的设计资产全部收口至本层，并按“看得见的 UI 零件”与“看不见的交互机制”一分为二：

1. **`shared-components.md`（有形跨页复用业务组件 `COMP-*`，组件较多时可拆入 `components/` 子目录）**
   - **概念解释**：指界面上**看得见、有明确视觉边界、内部组合了多个字段与按钮**的复合业务 UI 模块，且在不同页面挂载时往往存在细微的“场景变体”。
   - *通用示例*：
     - **商品摘要卡片 `COMP-ProductCard`**：在“首页推荐流”、“搜索结果页”、“我的收藏页”三处复用，主体都是封面图+标题+价格，但首页变体额外展示“推荐理由标签”，收藏页变体额外展示“取消收藏按钮”——在此处用一张变体矩阵表统一定义。
     - **数量步进调节器 `COMP-QuantityStepper`**：在购物车行与商详页规格区复用的 `[- 数量 +]` 控件（含最小起购量置灰、库存上限拦截反馈）。
2. **`interaction-patterns.md`（无形跨页交互行为契约 `PAT-*`，机制较多时可拆入 `patterns/` 子目录）**
   - **概念解释**：它不是某一个固定摆放位置的 UI 卡片，而是贯穿全站多个页面的**通用交互行为状态机、拦截恢复逻辑或全局反馈规范**。
   - *通用示例*：
     - **受限动作鉴权拦截与自动接续 `PAT-AuthResume`**：规定全站任何允许游客浏览的页面，当游客点击“收藏”、“加购”或“关注”时，系统先挂起该动作并弹出登录框；**一旦用户登录成功，系统必须自动替用户把刚才点击的“收藏/加购”执行完毕**，而不是只关掉登录框让用户再点一遍。
     - **破坏性移除延迟撤销条 `PAT-UndoSnackbar`**：规定用户在列表执行移除操作时，不弹烦人的二次确认框，而是直接从列表隐去并在底部浮出 4 秒“已移除 · [撤销]”提示条，倒计时内点撤销即可无损恢复。
     - **全局视图异常四态契约 `PAT-ViewStates`**：统一规定全站所有页面在“首屏加载中（骨架屏）”、“列表零数据（空状态引导）”、“网络请求失败（局部重试块）”、“轻量操作成功（顶部/底部轻提示）”时的标准交互行为。

### <a id="sec-3-5"></a>3.5 `06-pages/`：什么是“按功能空间建包 + 主页面与复杂子视图拆文件”？

- **第一层按业务板块（功能空间）建文件夹**：对应全站的一级导航模块及独立跨模块公共空间建立文件夹，让读者一眼看清产品有几大界面板块。
- **同一板块内“主页面”与“复杂附属子视图”平级拆文件**：一个简单的二次确认弹窗（只有一句话和两个按钮）直接写在主页面事件表里即可；但如果主页面挂了一个**字段繁多、自身也有多种状态的专属抽屉、侧边筛选栏或全屏专注子页**，就必须把它拆成同文件夹下的独立文件，防止主页面文档膨胀成数千行巨无霸。

```text
06-pages/
├── _index.md                            # 全站页面与子视图总注册表
├── search/                              # 板块 1：商品搜索空间
│   ├── search-result-main.md            # 主页面：搜索结果列表主页
│   └── advanced-filter-drawer.md        # 复杂附属子视图：多维价格/品牌/属性筛选抽屉（独立成篇）
├── checkout/                            # 板块 2：交易结算空间
│   ├── checkout-main.md                 # 主页面：确认订单主页
│   └── coupon-selector-drawer.md        # 复杂附属子视图：可用/不可用优惠券选择抽屉（独立成篇）
└── merchant-console/                    # 板块 3：[超大型板块下钻示例] 含十余个页面的商家工作台，继续按子模块分目录
    ├── _index.md
    ├── product-mgmt/
    └── finance-bill/
```

### <a id="sec-3-6"></a>3.6 `07-metrics-and-tracking/`：为什么要拆成“业务指标公式”与“底层埋点字典”？

为了根治业务团队“拍脑袋提一堆埋点却没人看”或数据团队“想算转化率却发现漏埋了关键属性”的脱节问题，本层强制拆分为上下咬合的两部分（事件较少时为两份单文件，事件上百个时升级为 `metrics/` 与 `events/` 两个子目录按模块分文件）：

1. **`metrics-funnel.md`（上层：业务看什么指标、转化率怎么算）**
   - **定位**：面向产品经理、业务方与数据分析师，定义衡量产品健康度的**北极星指标**与各核心模块的**漏斗转化率数学公式**（分子、分母必须精确写成底层埋点事件编号的运算组合）。
   - *通用示例*：定义 `搜索加购转化率 = 统计周期内触发 add_to_cart（且来源为搜索页）的去重用户数 ÷ 触发 search_executed 的去重用户数`。
2. **`event-dictionary.md`（底层：研发在代码里何时上报什么事件与字段）**
   - **定位**：面向前后端研发与测试工程师，逐条声明支撑上述公式所需的每一个**埋点事件英文名、在哪张页面/组件什么瞬间触发、必须携带哪些业务字段及数据类型**。
   - *通用示例*：定义事件 `search_executed`，在搜索结果页发起检索返回响应时触发，必传字段：`query_text (搜索词, String)`、`filter_count (启用筛选项个数, Int)`、`result_total (命中商品数, Int)`，并反向标明该事件用于计算“搜索加购转化率”。

### <a id="sec-3-7"></a>3.7 `08-verification/`：文字验收表与 `prototypes/` 下的四块内容分别干什么？

本层负责把静态文字规格变成“研发测试可逐条打勾的准出清单”和“无需搭建后端即可在浏览器点击体验的线框网页原型”，目录结构与各部分职责如下：

```text
08-verification/
├── acceptance-criteria.md               # 1. 文字版验收测试用例总表（用例极多时可拆为 acceptance/<模块>.md）
└── prototypes/                          # 浏览器双击即可打开体验的低保真可交互原型目录
    ├── index.html                       # 2a. 原型总导航入口页（汇总所有原型卡片与跳回规格书的链接）
    ├── shared/                          # 2b. 所有原型共用的底座（灰阶线框 CSS + 标准模拟假数据 JS）
    ├── pages/                           # 3. 单页面全状态演示原型（看单个页面在正常/空/报错下的不同长相）
    │   ├── search.html
    │   └── checkout.html
    └── flows/                           # 4. 跨页面串联演示微原型（看 2~3 个页面之间的数据传递与拦截恢复）
        └── guest-buy-resume.html
```

1. **`acceptance-criteria.md`（文字版结构化验收清单）**
   - **职责**：将核心业务流程及 `03` 层中容易漏测的边界条件、异常兜底写成确定性的 `前置条件 → 触发操作 → 预期结果` 核对表，供研发提测自检与 QA 准出打勾。
   - *通用示例*：`前置` 账户有 1 张满 100 减 20 券且购物车商品合计 105 元 → `操作` 在结算页取消勾选其中 10 元商品使合计降至 95 元 → `预期` 自动取消该券勾选，实付更新为 95 元并提示“还差 5 元可用券”。
2. **`prototypes/index.html` 与 `prototypes/shared/`（总入口与共用低保真底座）**
   - **`index.html`**：原型目录首页，把下面所有的单页原型和跨页原型列成清晰卡片，方便评审者一键点开。
   - **`shared/`**：统一存放灰阶线框样式（不搞花哨配色，专注布局与信息层级）和一份与 `02` 层字段对齐的标准假数据，避免不同原型页各自编造矛盾的商品或用户信息。
3. **`prototypes/pages/*.html`（单页全状态线框原型）**
   - **解决什么痛点**：传统原型想看一眼“搜索零结果”或“网络报错”，往往要先手动输入乱码或断网折腾半天。单页全状态原型在**网页最顶部固定放一排状态切换按钮**（如 `[S1 正常有结果]`、`[S2 未登录游客态]`、`[S3 搜索零结果]`、`[S4 网络断开异常]`）及 `[手机 / 平板 / 电脑]` 宽度切换按钮——点一下按钮，下方画面立刻切到对应状态。
4. **`prototypes/flows/*.html`（跨页关键动线微原型）**
   - **解决什么痛点**：单页原型只能看单个页面的静态切面，看不出跨页面操作时的动态衔接。`flows/` 专门挑选全站最关键的 2~3 条跨页链路做成独立小网页。
   - *通用示例*：打开 `guest-buy-resume.html`，亲手点击体验“游客在商品页点立即购买 → 拦截弹出登录框 → 点击模拟登录成功后，无需重回商品页再点一次，系统自动带着刚才选好的尺码数量直达确认订单页”的完整跨页传递过程。
